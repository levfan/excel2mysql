## 13. 第六轮：查"代码存在但从没跑过"的功能面（补了两个验证洞）

### 13.1 `.xls`（97-2003 老格式）——帮助文档里写着"两类 Excel 格式"，七个夹具却全是 `.xlsx`

新增 `java/tools/export_xls_golden.py`（xlwt 写文件，期望值仍取自真实 pandas + xlrd 与真实
`core.build_table_def`），产出六张夹具与 `java/verify/golden/xls.jsonl.gz`：

实测结果：`READER-DIFF 表 5 张 | 比对 48 格 | 不一致 0 处`、`TYPE-DIFF 列 16 个 | 0 处`、
`NAME-DIFF 不一致 0 处`。几条容易想当然的老格式语义，现在是有数的而不是"应该一样"：

- 整数值的日期序列号 `46000` 被 xlrd 读成 **int**，`46000.5` 才是 float；

### 13.2 结构定义表（元数据 Sheet 驱动）——整条路只有代码存在，没有证据

`build_table_def` 有两条路：普通表靠推断，元数据表靠用户在 Sheet 里手写字段名/类型/注释。
两个差分器都按各自理由跳过了后者：`NameDiffer` 比的是拼音规则（这里名字是手写的，比了必然假红），
`TypeDiffer` 比的是推断器（这里类型来自元数据）。**两边都跳，等于这条路没人管。**

补法：`ReaderDiffer` 对 `source=structured` 的记录直接跑 Java 整条 `TableBuilder.build(path)`，
把表名、基础表名、表注释、来源、主键、主键理由和每列的字段名/类型/可空/主键标记逐字段比。
摘要行加了计数（`结构定义表端到端比对 1 张`），防止"看起来在跑其实被 continue 掉了"。

连表定义都没有（`build_table_def` 直接拒），所以它不比表名，改撞"Java 也拒绝"：
`NAME-DIFF 合并拒绝 1 个`、`READER-DIFF 合并区检测 6 个文件（其中按拒绝记账 1）`。
`NameDiffer` 因此要真打开文件，构建脚本里它的 classpath 补了 `verify\target\lib\*`（POI）。

### 14.1 差分方法：比"写出来的文件"，不是比"各自回读自证"

写出同一个文件——两条线完全可以各自"内部一致"地写出不同东西，回读照样全绿。
所以加了一份跨线金标准：

- `java/tools/export_meta_golden.py` 用 Python 线真写出 24 份文件（12 夹具 × 标准/简易），
  用 openpyxl 原样读回逐格编码（不经 pandas，免得列名去重、空行裁剪混进来），
  连同 Python 把自己那份读回来得到的表定义一起写进 `verify/golden/meta.jsonl.gz`；
- `verify/.../MetaDiffer.java` 用 Java 线写同一批夹具、读自己写出的文件，
  逐格比对命名、Sheet 名、目录前缀、元数据七列、数据区每一格，
  再把 Java 那份读回来的定义与金标准里那份逐字段比。
  闸门第 9 步：`META-DIFF | 记录 24 条 | Sheet 36 个 | 比对 2133 格 | 不一致 0 处`。

### 14.2 这条新功能顺手挖出一个已存在的读取层缺陷（已修）

第一次跑 `MetaDiffer` 报 345 处不一致，归因后只有一类，但它是真缺陷：
`水库基础信息（dim_reservoir_info）.xlsx` 有一整列纯空白的数据，Python 线给出 17 列，
Java 线只给出 16 列——FastExcel 默认 `autoTrim` 把 `"   "` 裁成空再变成 null，
`dropEmptyColumnsAndRows` 就把整列删了，DDL 少一个字段。

三步差分为什么都没抓到：`READER-DIFF` 对纯空白格做了"按空值等价"的折叠（当时 Java 侧
确实是 null），`TYPE-DIFF` 喂的是金标准里已解码的网格、不经过真实读取器，
`NAME-DIFF` 不比列数。也就是说这条路径上从来没有一个测试真走过"读文件→出表定义"。

修法：`WorkbookReader` 关掉 autoTrim（`.autoTrim(Boolean.FALSE)`），并把 `ReaderDiffer`
里两侧的空格折叠摘掉，改成原样比——现在 `纯空白格 2 格（两边同值）`，不再靠折叠遮丑。
界面渲染图上也看得见：文件表里这张表的字段数从 16 变回 17。

### 14.3 界面侧的取证与守卫

`--gui --selftest` 新增 `meta_export` 一段，断的都是可数的副作用：

  停止 / 开始导入 / 标准 / 简易（`getParent()` 同一个容器 + 组件序）；
- 启用条件：有表才可点，`startTask()` 期间必须变灰，`clearAll()` 后回到灰；

- 真按一次走 `programDir()`：断言 `app\target\meta_data_file_年月日` 下文件数等于表数、
  每个文件是元数据+数据两个 Sheet、七列表头一字不差、能被 `TableBuilder` 当结构定义表读回，
  验完删掉自己造的目录；

## 15. 第八轮：把"两条线功能一致"变成机器判定（双端枚举对撞器）

前七轮的验收面是我自己列的清单，清单想到哪儿就只验到哪儿。这轮换办法：
**从两条线的活窗口上机器枚举界面事实，落成同名 key，逐键对撞**。

### 15.1 对撞器

- `java/tools/gui_dump_py.py`（Qt 侧）与 `java/verify/.../GuiDump.java`（Swing 侧）
  各跑同一套脚本：建窗 → 空态 → 加载 12 个夹具 → 加/换前缀 → 开五个弹窗 →
  真点两颗生成按钮读回产物 → SQL 页加两个脚本并改前缀 → 清空待上传文件；
  每一步把控件类别、文案、tooltip、占位、启用态、表格列与行、日志、弹窗
  （图标+标题+正文）写成 `key = value`。
- `java/tools/gui_parity.py` 跑两端再逐键比，`java/界面双端对撞.bat` 是一键入口。
  当前 **170 个键逐键一致**。
- 归一是有意为之且写明了理由：类名（QLineEdit vs JTextField/HintTextField）折成控件类别词表；
  tooltip 的换行是载体决定的（Qt `\n`、Swing `<br>`），抹掉换行再比话术；
  导出产物里的数字**按值比不按字面比**（同一个 1e25，openpyxl 原样给浮点、POI 归一成整数）；
  连接失败的缩进明细行是驱动原文（pymysql 2003 vs JDBC Communications link failure），
  固定文案那一行照比，明细由 `guard.conn.*` 单独断"有没有"。

### 15.2 对撞器查出的四处真差距（都已修）

1. **「开始导入」的启用条件**：Python 是"有表就能点"，没选库由入口弹 NO_DB_HINT；
   Java 额外要求已连接，于是同一份列表在两条线上按钮一亮一灰。改成 Java 跟 Python，
   并把 Java 自检里那条"未连接时不该可点"的断言翻过来（它当初把设计选择当成了契约）。
2. **清空待上传文件后「开始导入」还亮着**：Python 的 `on_clear` 会把它置灰，Java 的 `clearAll` 漏了。
3. **页内进度条不印百分比**：Qt 的 QProgressBar 默认在条上画 `0%`，Swing 默认什么都不画。
   补 `setStringPainted(true)`。这条只有渲染成图才看得见，读代码读不出来。
4. **空点「停止」在 Python 侧是静默 no-op**：Java 会写一行"没有正在执行的任务"。
   按"用户动作必须留可见痕迹"的口径，这次是 Python 补齐。

另外两处顺带对齐：Python 的七处拦截弹窗（没选库 / 没表 / 前缀为空或非法）现在与 Java 一样
**日志与弹窗双写**同一句话（`已拦下：……`）；Java 的 `describe()` 在 vendor code 为 0 时
不再打"（MySQL 错误码 0）"——连不上库时那个 0 是驱动没给码，写出来会让人以为服务端回了错。
`critical()` 也改走 `dialog()`，于是原地模式下不再把事件分发线程卡死（对撞器正是被这个卡住的）。

### 15.3 守卫的可红性

把 Java 侧"没有正在执行的任务"改一个字符 → 对撞器报 `guard.stop` 值不等，

## 16. 第九轮：三条探针从"代理"改成"真做一件事"，三条线的区别打进产物

### 16.1 `dblclick` 从"线接没接"改成"真开一次弹窗"

原来的断言是 `getMouseListeners().length > 0` / `receivers(...) > 0`，
那只能证明信号线上挂了个东西，证明不了点开的是不是那一张表。改成两侧真的建弹窗：

- Python：把真 `StructureDialog` 子类化，只替换模态的 `exec()`（记一笔、返回取消），
  所以表体、标签页都是真渲染出来的。直接 `emit(0, 0)` 走的是真接线。
- Java：这里踩了一次死锁——`StructureDialog` 是**模态**的，
  把派发放在枚举主体的 `invokeAndWait` 里，`setVisible(true)` 就在 EDT 上开了第二层
  事件循环，整份枚举卡住（`java.exe` 挂了一分多钟不退出，量到的还是上一份残留 json）。
  改成：派发丢 `invokeLater`，由非 EDT 线程轮询 `Window.getWindows()` 等窗口出现，
  再 `invokeAndWait` 读标签页并 `dispose()` 放行（模态嵌套循环仍会处理事件队列，
  所以这个 `invokeAndWait` 进得去）。10 秒等不到就记 `0|0|sel=… seen=…`，
  是红线不是静默跳过。
- 两侧同报 `1|1|ren_yuan_xin_xi_biao_ren_shi_chu`。

顺带查出一条**真差距**：Java 双击文件列表只弹那一行的表，Python 之前弹整张列表——
组框标题写的是"双击表名/字段可编辑"，弹整张列表等于让用户猜改的是谁。
Python 补 `on_edit_structure_row(row, col)`：只装那一行、回写只替换那一条。
日志也补齐：确认后 Java 的 `[结构] xxx 已按弹窗修改` 与按钮路径的
`[结构] 已按弹窗确认 N 张表的字段定义`，Python 现在两条都有（Java 按钮路径本来就写，
Python 之前两条都不写，属于"改完了界面上没痕迹"）。

### 16.2 `window.size` / `window.icon` 是两边探针不同源

- 尺寸：Qt 顶层的 `resize` 说的是客户区，Swing 的 `setSize` 说的是外框。
  Java 早先用 `setPreferredSize + pack` 把内容面板钉成 1100x780（外框 1122x836 由系统加），
  而探针还在量 `getWidth()`——所以"差 22x56"差的是操作系统那条标题栏，不是界面。
  两侧统一改成量客户区 / 内容面板，`GuiMain` 的断言同步改成
  `frame.getContentPane().getSize()`；顺手删掉构造里已被 `pack()` 覆盖的那句 `setSize`。
- 图标：Python 报 `none` 不是产品没图标，是探针绕过了生产入口——
  `setWindowIcon` 原来写在 `if __name__ == "__main__":` 里，对撞器自己 `MainWindow()`
  就永远看不到。把应用级设置提成 `setup_app(app)`，`__main__` 与对撞器都调它，
  两侧同报 `max=256`。

## 17. 第十轮：弹框首屏看得全，四条形态与随包必备件核对

### 17.1 起因与实测到的两类遮挡

用户要求"弹框尺寸合适，首次打开就能看到全部文字，不要遮挡"。先量了最坏文案，两类问题都是实测的：

- **Swing 的消息框折不了一行**：一条上百字符的产物目录把 `JOptionPane` 撑到 **1286 像素宽**，
  在 1024x768 的老屏上右边那半截直接看不见（`JLabel` 对纯文本按一行画，`\n` 之外不折）。
- **Qt 会折但会撑高**：同样那份 `QMessageBox`，30 行正文的量结果是 **400x894**，
  比屏幕可用高度还高，底部若干行看不见；而"一条长路径"那一例它报 737 宽。
  也就是说两边对同一句话的排版完全不同——这既是遮挡问题也是对撞口径问题。

### 17.2 折行与限高自己算，两边同一套规则

- Python：`main.wrap_popup_text()`（`unicodedata.east_asian_width` 判 F/W 为 2 列），
  所有消息弹窗改走 `main.popup_box(...)` 这一道（原来是 11 处直接调 `QMessageBox.*`）。
- Java：`gui.PopupText.wrap()` 用一份显式的宽字符区间表实现同一口径，
  `MainFrame.dialog()` 显示与记录都用折好行的那份。
- 契约数字写死：**72 显示列（约 36 个汉字）/ 24 行**，超出部分换成
  「……（其余 N 行放不下，完整内容见底部日志）」——日志里一直是完整的那份。
- 进度框的状态行原来靠 CSS 定宽（`<body style='width: 430px'>`），实测那条会让
  `JLabel` 把整篇文档宽度当成自己的首选尺寸，把进度框顶到 **583 宽**（Python 是 480）。
  改成同样走 `PopupText.wrap` 再把换行换成 `<br>`，进度框回到 480x140。

### 17.3 窗口尺寸：钉客户区 + 按真实外框夹屏幕

- 新增 `ui_help.fit_client()` 与 `gui.Windows.clientSize()`：配置值按客户区给，
  夹取时**量真实外框**（`win.getInsets()`），而不是用猜的常量。
- 这里被自己的新断言抓到过一次实现错误：第一版用写死的 48 像素当标题栏+边框，
  而这台机器实测是 56，于是"要求 99999 宽"仍然超可用区 8 像素。改成 pack 之后量真实
  insets 再回夹（最多 4 轮），断言才过。
- 夹取用**内容的最小尺寸**兜底而不是首选尺寸：`QTextBrowser`/`JEditorPane` 的首选尺寸
  等于整篇文档，拿它兜底会把说明窗撑到 2550 宽；最小尺寸很小，所以说明窗钉回 960x700。

## 18. 第三轮：zip 现场报错的加固，与新增的「SQL 执行器」页签

用户这轮提了两件事：现场 Win10 上拖 ZIP 进来就报错；要第三个页签能直接执行 SQL，
带问号图标打开示例，常见与数据治理用的各凑 30 条。

### 18.1 zip 那条：本地复现不出来，就把会炸的每一处都改成不炸或说人话

七种 zip 形态（单层、多层目录、包内嵌套、中文名、GBK 名、超长路径、含非 Excel）
加用户那份真包，都过 GUI 的"拖入→解析→导入"整条路跑过，本地一次都没重现出报错。
既然现场条件量不到，就把四类成因逐个消掉：

| 成因 | 处理 |
| --- | --- |
| 解压后的绝对路径超出 260 | `ZipImport.PATH_BUDGET = 240`（给短文件名转换留 20）；超预算时先尝试把条目平铺到根目录，平铺后仍超或撞名才拒，并给出"把包拷到短路径目录（如 `D:\data`）再拖，或改短 `TEMP`" |
| 临时根目录本身很长 | 解压根改成 `e2m-<纳秒>`（原先带毫秒与更长的前缀） |
| POI 的 zip bomb 阈值误杀高重复列的业务表 | `ZipSecureFile.setMinInflateRatio(0.000d)`；实测 4 万行重复列在 0.01 与 0.001 下都读得进来，因果没被证实，改这一处是按威胁模型取舍，代价写进 README 的已知限制 |
| 成功文件移出列表后 Swing 仍按旧行号问 tooltip，越界抛异常 | `FileRowModel.tooltipAt` 加边界守卫返回空串 |

用户随后的反馈是"现在确实不报错了"。这一轮的取证强度到此为止：
本地从未重现，所以给不出"现场那一下究竟是哪个原因"的结论，只能保证
四类成因里每一类要么不再发生，要么发生时说得清下一步做什么。

### 18.2 新页签的结构：一份示例源，两条线各自导出

`sql_samples.py` 是 30 条示例的唯一来源（5 组：建库与选库 4、建表与改表 10、
元数据与治理体检 9、查询与执行计划 4、数据修正 3），Java 侧
`tools/export_sql_samples.py` 导出成 `SqlSamples.java`，与 HelpDoc 同一个套路。
执行本体也成对：`core/sql_execute.py` 与 `core/SqlExecute.java` 文案逐行对齐，
事务语义一致（全部成功才提交、中途出错整批回滚、失败那句后附 DDL 隐式提交提醒）。

页面上：提示单独一行、`示例 (?)`/`执行`/`清空` 另起一行——原先挤在同一行时，
QLabel 的最小宽度就是整句宽度，加上三颗按钮把整窗最小宽度顶到 830 以上，
1024x768 的现场机和 800 宽的离屏用例都放不下（用例 U7 抓到过一次）。
示例对话框非模态：这一页的用法是边看清单边改语句，模态框等于让人抄两遍。

### 18.3 这一轮顺带修掉的两个真缺陷

- **`LogPanel` 的 `ConcurrentModificationException`**：工作线程在 `append()` 里直接动
  `entries`，事件分发线程同时在 `render()` 里遍历它。真库端到端探针第一次跑就在
  `AWT-EventQueue-0` 上炸出来。现场后果不是崩溃而是"日志跑到一半不再刷新"——
  那次事件被异常带走，用户只会以为程序卡死。改法是所有 `entries` 访问共用一把锁，
  `render()` 先取锁内快照再往文档里写；收行仍留在调用线程，自检"写完立刻读"的口径不变。
  变异抽查：把八处 `synchronized (entries)` 换成 `synchronized (new Object())`（等于没锁），
  自检两次都红（`写线程炸了 java.util.NoSuchElementException`）；换回真锁三次绿。
- **Python 那份执行器逐句提交**：本体里每执行一句就 `conn.commit()`，
  与 tooltip 说的"全部成功才提交，中途出错整批回滚"相反——真出事时前面已写入的数据撤不回来。
  同时 `-- 只有注释` 会被 `split_sql_statements` 当成一句执行掉，界面上报"已提交 1 条"，
  而那句里根本没有语句，且文案明明写着"只写注释也不算"。改法是执行器只认
  `has_executable_content()` 为真的句子（与切句同一套词法，字符串里的 `--` 不算注释），
  并把批内提交收成一次。Java 侧同样加 `SqlScript.hasExecutableContent` /
  `executableStatements`，判据表 13 格两边各断一遍（pack_test E10/E11 与 `GuiMain`）。

### 18.4 生成物漂移闸

`help_doc.py` 改了正文但没重导 `HelpDoc.java`，双端对撞抓不到（它只比目录标题），
本轮就差点让 `jre\bin\java.exe` 那处转义修复只落在一边。新增
`java/tools/check_generated.py`：重跑两个导出脚本，把生成结果与仓库里那份逐字节比，

所以 Java 线交付闸门第一步就先问"这两份生成物是不是手抄的"。
变异抽查：往 `help_doc.py` 的一节里插一句，检查器红并打印差异行。

顺带修掉一个显示层的老缺陷：`help_doc.py` 里 `jre\bin\java.exe` 写在非 raw 字符串里，
`\b` 被吃掉成退格符，说明窗与随包手册里那行路径是坏的（`jre<退格>in\java.exe`）。
现在按字面写着，且用例 P3b 断"正文里不许出现控制字符、这行路径要按字面在"。

### 18.5 第二个页签改名：「SQL 脚本」→「SQL 脚本改名入库」

用户按功能提的改名。这页干三件事，按顺序是：把脚本里的
`CREATE TABLE` 提取出来并数出现次数（表格那三列就是这个清单）、按这份清单批量改表名
（加前缀 / 换首段，引用一并同步改）、然后把改好的脚本另存副本或执行到当前库。

所以名字取区分度最高的两步——改名与入库；第三个页签叫「SQL 执行器」，
说的是"临时执行一段"。两页的分工在《使用说明》两章开头各写了一句，

按钮文案不动（`添加 SQL 文件`/`批量应用前缀`/`替换首个前缀`/`保存修改后ddl脚本`/
`执行修改后ddl脚本到当前库`），提示条那句"SQL 脚本将执行到这个库"也不动——它说的是内容不是页签。

## 19. 第四轮：第二个页签加「生成标准/简易 excel文件」，顺带顶出退出时的闪退

用户提的是"第二个 tab 页也需要这两个按钮"。做完之后真正的收获不在按钮上：
两条 GUI 线界面上多两颗按钮，把 Python 那条线**解释器退出时偶发的 access violation** 顶成了必现，
根因、修法和对闸门的影响都记在 19.4。

### 19.1 数据源换了，产物形状不许换

「Excel 导入」页那两颗按钮吃的是"已经解析好的表 + 数据行"；这一页只有 `.sql` 文本，
所以新增一条路：读脚本正文 → 解析 `CREATE TABLE` 的列定义 → 交给**同一个** `meta_export` 出口。
标准件仍是「元数据」+「数据」两个 Sheet、简易件仍只有「数据」，
日期目录名、文件命名（`表注释（表名）.xlsx`）、进度计项、取消语义、
"日志 + 弹窗双写"全部沿用，两条线共用一份口径，不另开一套形状。

因为脚本里只有结构没有数据，「数据」Sheet 只剩英文字段名那一行表头。
这一点写进 tooltip、《使用说明》与 README，定位成"给下游填数据的模板"，不假装里面有数据。

生成取的是**改名之后的当前正文**，所以"先批量改前缀、再生成交付件"这条路是通的，
产物里的表名就是新表名（对撞键 `sqlgen.*` 与用例 R41 都钉住这一条）。

### 19.2 解析只能近似，就必须逐列点名

元数据 Sheet 的读回端只认「一个类型关键字 + 纯数字长度」（`_norm_meta_type` /
`_norm_meta_length`），DDL 里的东西比这个形状宽得多。近似规则和对应的说明：

| DDL 写法 | 落到元数据 | 日志说明 |
| --- | --- | --- |
| `bigint(20) unsigned` | `BIGINT` + 长度 `20` | `列 id 的 BIGINT(20) 装不进元数据 Sheet，按 BIGINT 导出（丢了 UNSIGNED）` |
| `varchar(64) character set utf8mb4` | `VARCHAR` + `64` | 同上，丢了 CHARACTER SET |
| `enum('a','b')` | `TEXT` | 括号里不是数字，照原样写会产出只有 ENUM、没有取值的非法 DDL |
| `CREATE TABLE t LIKE s` / `… AS SELECT` | 不导出 | 这条语句里没有列定义 |
| 同名表定义两次 | 只按第一处 | 说明是哪一处被采纳、哪一处被跳过 |

`! [WARN] 说明 |` / `! [WARN] 跳过 |` 逐条落在这一页自己的日志区，不静默改语义。
建表那侧的口径也一起对齐：主键列写「是否可为空=否」，其余写「是」，
所以生成件能被本工具原样读回（R38、`sqlgen.roundtrip`、META-DIFF 三处分别钉住）。

新增 `core/sql_script.parse_create_tables()` 与 Java `SqlScript.parseCreateTables()`，
两条线共用一份金标准语料（`java/tools/ddl_corpus.py` 生成的 6 份脚本，含复合主键、
unsigned、charset、enum、重名、LIKE/AS SELECT、反引号里带 ``we``ird`` 、空括号、括号不配对），
`SqlDiffer` 加 `ddl-parse` 分支后比对 **295 项、不一致 0 项**。
这一轮里差分器真抓到过一个解析缺陷：`CREATE TABLE x LIKE y` 会把下一条语句的 `(` 抢走，
原因是语句边界没界定住——改成"分号与下一条 `CREATE TABLE` 之间取近者"才对。

### 19.3 对撞器加的键

从 209 键到 **218 键**，新增 9 个：

- `btn.SQL 脚本改名入库.生成标准excel文件.on` / `.tip`、
  `btn.SQL 脚本改名入库.生成简易excel文件.on` / `.tip`（四件套由枚举器自动覆盖，
  这一页的判据是"有没有脚本"，不是"有没有解析出表"）
- `sqlgen.log`：清场 → 只喂一份 probe 脚本 → 连点两颗按钮，把整段日志（解析说明、
  逐文件导出行、`===== 生成完成 =====`）归一化掉临时根目录与日期目录名后逐字比
- `sqlgen.popup`：最后一次「生成结果」弹窗的图标、标题与正文
- `sqlgen.std.content` / `sqlgen.simple.content`：两个产物目录里每个 xlsx 的 Sheet 名与逐格值
- `sqlgen.roundtrip`：用**本条线自己的读取器**把标准件读回来，渲染成
  `source|表名|表注释|字段:类型:pk` 一行；读不回就是缺陷，不靠"看起来一样"

两边喂的是同一份脚本正文、同一份夹具，比的是产物与说的话，不是各自"跑通了"。

### 19.4 界面上多两颗按钮，把退出时的闪退顶成必现

现象：`pack_test.py` 用例全绿（449 通过 / 0 失败），但**进程退出码是 127**，
faulthandler 打的是 `Windows fatal exception: access violation` + `Fatal Python error: Aborted`，
且 `Current thread … <no Python frame>`——崩在原生层，Python 栈已经没了。

定位过程（每一步都留了证据）：

| 试的东西 | 结果 |
| --- | --- |
| HEAD 整轮 vs 工作区整轮（同机、并行跑） | HEAD 退出 0，工作区退出 127 |

## 22. 执行结果排成等宽表格（"没有任何样式，很难阅读"）

用户对着第三个页签的结果区说的这句。原来的输出是把取值用 `" | "` 直接拼一行：

```
      id | 名称 | amount
      1 | 某公司 | 3.50
      10 | 很短 | NULL
```

列宽不一样就错行，混进中文之后连列名都对不上是哪一列。改成边框表格：

```
+----+--------+--------+
| id | 名称   | amount |
+----+--------+--------+
| 1  | 某公司 | 3.50   |
| 10 | 很短   | NULL   |
+----+--------+--------+
```

### 22.1 定下来的渲染口径（两边必须逐字符一样）

- 列宽 = 表头与该列预览取值的**显示宽度**最大值；宽度按显式区间表算，
  汉字/全角占 2 列（Python `core/text_width.py`，Java `core/TextWidth.java`，区间逐条对齐）。
  **不用 `unicodedata.east_asian_width`**：那张表跟 Unicode 版本走，Python 升一次版就可能改口，
  而这条规则的两端是两份语言的实现，必须在任何机器上给出同一个宽度
- 每格前后各一个空格，列与列之间 `|`，上下与表头下面各一条 `+---+` 分隔线；
  **零行时不重复画收口线**（表头下面那条就是收口）
- 空格子写 `NULL`；取值里的换行与制表符写成可见转义 `\n` / `\t`
  （一条带换行的备注能把整张表顶散）
- 单格超过 40 显示列截断并补省略号
- 行比列少补**空格**而不是 `NULL`：少给值不等于值是 NULL
- 缩进仍是语句行下面那 6 个空格，`共 N 行（只打印前 200 行，其余没显示）` 那句话原样不动

### 22.2 差分与字体

中英混排、零行、无列名、换行/制表/超长、全角与假名与生僻字 `𠀀`、多列、行比列短/长、
空串与 NULL 同列）。取值一律只用字符串与 None——数字的 `str()` 在两边本来就不一样

## 23. 表头带必填星号就"解析不到表头"——星号是清白的，凶手是 dropna

用户报"表头数据有必填项，比如【*标准名称】，会解析不到表头数据"。先按字面复现：
`*标准名称` / `【*标准名称】` / `＊备注`（全角）/ `标准名称*` 各种写法，**两条线都能正常解析**，
星号不进字段名、原文留在字段注释里（`core/infer._syllables` 把非 `\w` 字符换成下划线再切）。
所以星号本身不是原因。真正丢东西的是读表后的那一句：

```python
df = df.dropna(axis=1, how="all")     # 整列没值就删
```

这条规则不看表头写没写字，于是：

- **必填列整列没填**（`*填报人` 这种）被静默删掉——现场看到的就是"表头解析不到"；
- **只有表头的采集模板**一列不剩，直接被 `没有解析到任何字段` 整份拒收。

### 23.1 改后的判据：看表头写没写字

| 列的形状 | 处理 | 理由 |
| --- | --- | --- |
| 表头有字（含 `*`、`＊`、`【】`）+ 整列没值 | **保留**，并记进 `empty_columns` | 字段是使用方声明过的表结构，删它等于把表改小一号 |
| 表头空着（pandas 里叫 `Unnamed: N`）+ 整列没值 | 丢掉 | Excel 尾部格式化拖出来的垃圾列，本来就不是字段 |
| 整列都是空字符串 `""` | 保留，且**不算**空列 | 判空只看 `isna`，与原来 `dropna` 同口径，不顺手扩权 |
| 全空行 | 照旧丢掉 | 避免整行 NULL 入库 |

另外两条跟着一起定：`no_data_rows`（一行数据都没有）随表定义一起返回，
`[已解析]` 那行末尾追加"整列为空的字段照旧保留：…（>6 个折叠成"等 N 个"）"与
"没有数据行，建出来是空表"；主键自动选择在零行时本来就不选（`select_primary_key` 已有那道闸），
自检里再钉一次。手工勾选不受这条限制：空表在非空与唯一上天然成立，类型合规即可保存
（见第 32 节）。

### 23.2 一条规则只许有一处实现

Python 是 `core/infer._named_blank_columns` / `_drop_unnamed_blank_columns`；
Java 是 `TableBuilder.filterColumns`，**读取层和 `TypeDiffer` 都调它**。

## 24. 第五轮：表头里的括号注释不该跟着进字段名

用户接着报第 2 件："excel 表头中，还会有特殊符号，你都要去掉。比如：发布日期（yyyy-MM-dd），

### 24.1 先量清"哪些符号真的进了名字"

拿 28 种真实表单写法喂现有的 `_col_to_field` 打了一遍（临时探针，不进仓库），结论是
**符号本身早就不进了**：`_syllables` 第一步 `re.sub(r"[^\w]+", "_")` 把 `*`、`＊`、全角空格、
`：`、`、`、`①`、`&`、`★` 全折成下划线再丢弃，所以上一轮那批星号是清白的，这一轮也是。

真正进名字的是**括号里那串内容**——它不是符号，它被当成正文转写了：

| 表头 | 改前 | 改后 |
| --- | --- | --- |
| `发布日期（yyyy-MM-dd）` | `fa_bu_ri_qi_yyyy_mm_dd` | `fa_bu_ri_qi` |
| `金额（元）` | `jin_e_yuan` | `jin_e` |
| `是否已婚【是/否】` | `shi_fou_yi_hun_shi_fou` | `shi_fou_yi_hun` |
| `★（必填）联系电话` | `bi_tian_lian_xi_dian_hua` | `lian_xi_dian_hua` |
| `累年月日降水量≥1.0mm平均日数(d)` | `lnyrjsl10mmpjrsd` | `lnyrjsl10mmpjrs` |

所以这条需求落在"成对括号整段不进名字"，不是"再多剥几个符号字符"。

### 24.2 定下来的规则（两侧同一份口径）

1. 左括号到右括号**整段**去掉。括号清单按**码位**写死，两侧同源：半角 `()` `[]` `{}`、
   全角 `（）` `［］` `｛｝`、`【】` `〔〕` `〈〉` `《》` `「」` `『』`。
2. 嵌套最多剥三轮，最后再把配不对的**孤立括号符**删掉。第一版只跑一轮，
   `单价（含税（13%））` 会剩一个右括号变成 `dan_jia_`。
3. **整格就是括号时不剥空**（`（备注说明）` 仍出 `bei_zhu_shuo_ming`），否则退化成 `col`。
4. **只作用于字段名**。列注释仍是原始表头，口径信息一个不丢；表名不受影响
   （文件名那条 `（英文表名）` 另有规则，别顺手统一）。
5. 不做"括号里是合法英文标识符就拿它当名字"这种例外。看着像文件名规则的延续，
   但 `填表日期（YYYYMMDD）` 会被它带偏成 `yyyymmdd`——用户要的是 `填表日期`。

### 24.3 顺带把去重收成一处实现（差分器逼出来的）

剥完之后 `发布日期（yyyy-MM-dd）` 与 `发布日期` 同名，金标准里 Python 出
`fa_bu_ri_qi` / `fa_bu_ri_qi_2`，Java 的 `NameDiffer` 却报
`期望=fa_bu_ri_qi_2 实际=fa_bu_ri_qi`。不是 Java 算错：差分器逐列**独立**调 `colToField`，
而 `_2` 是 `inferColumns` 里那份 `seen` 状态给的——去重规则写在调用方，撞名这一类形状它天生看不见。
于是两侧各抽出一个 `dedup_field(seen, field)`（Python `core/infer.py`、Java `Names.dedupField`），
读取层与差分器都调它，"一条规则只留一处实现"这条老口径这回落在了去重上。

## 26. 用户把同一句话又说了一遍：漏的是没括号与没配对的写法

用户第二次发"表头中还会有特殊符号，你都要去掉，比如 发布日期（yyyy-MM-dd） 要提取成 发布日期"。
第 24 节那条已经落地并在产物里验过，所以这次**先证明"他举的例子是好的"，再找他真正会撞上的写法**：
拿 30 多种表头喂当前代码（`head_leak_probe`，临时探针），三种还在漏：

| 表头 | 漏出来的字段名 |
| --- | --- |
| `发布日期：yyyy-MM-dd` / `发布日期 yyyy-MM-dd` / `发布日期/yyyy/MM/dd` | `fa_bu_ri_qi_yyyy_mm_dd` |
| `发布日期（yyyy-MM-dd`（右括号忘配） | `fa_bu_ri_qi_yyyy_mm_dd` |
| `发布日期〖yyyy-MM-dd〗`（方头括号不在清单里） | `fa_bu_ri_qi_yyyy_mm_dd` |

**教训**：用户给的是"例子"，不是"边界"。上一轮把规则写成"只在成对括号里才剥"，
等于假设填表人都把括号配齐 —— 现场手写表头漏右半边、干脆不打括号都极常见。

### 26.1 一般化后的规则（两侧同一份码位与同一份正则）

1. 括号清单补 `〖〗`（U+3016 / U+3017）。
2. **左括号没配右半边** → 从它起整段丢（`_ANNOT_OPEN_TAIL_RE`，`DOTALL` 让换行也算在内）。
3. **日期时间格式掩码串即使没括号也丢**（`_MASK_SEG_RE`）：首段 `[yYmMdDhHsS]{2,}`，
   分隔符允许 `-` `/` `–` `_` `.` `:` `：`，后续段可以是纯数字。

掩码判定最容易越界吃掉真名字，所以写了三条**反向守卫**（M19 / M19b / M19c）钉住不扩大：
`1.0mm` 里的 `mm` 前贴数字不算掩码；**表头不含汉字时整条不参与掩码判断**
（`MM-dd`、`qty` 这类纯英文列名就是名字本身）；`2020-01-01` 首位是数字所以不算掩码。
另有一条兜底：剥到一个字段都不剩时不剥（`yyyy-MM-dd` 单独作表头仍出 `yyyy_mm_dd`，不变 `col`）。

### 26.2 这条与第 25 节不同，金标准撞得出

掩码是纯字符串规则，不依赖读取层留没留信息，所以直接把 `表头带注释（ods_t_head_note）`
夹具从 7 列加宽到 12 列（新增没括号、没配对、方头括号、以及一条 `1.0mm` 反向样本），
四个导出脚本按派生链重跑。闸门里 `NAME-DIFF` 从 46 字段涨到 **51 字段**、`TYPE-DIFF`
同步，不一致均为 0 —— 两侧真的算出同一份名字，不是各自自我声明。

## 28. 添加文件弹窗：文件名框里输入文件夹路径回车要进目录

用户点虚线区打开文件选择器后，在文件名框里写入文件夹路径并回车，期望是打开该目录继续挑文件，
而不是把目录当成选中文件交给程序。

### 28.1 实测分界

| 操作 | Python 图形版（Qt 原生弹窗） | Java 图形版（修改前） |
| --- | --- | --- |
| 输入文件夹路径（不带引号）后回车 / 点「打开」 | 进入该目录，弹窗不关 | 进入该目录，弹窗不关 |
| 粘贴 `"D:\…\目录"`（资源管理器「复制文件地址」的格式）后回车 / 点「打开」 | 进入该目录，弹窗不关 | 把目录当成选中文件关闭弹窗 |
| 选中真实 Excel | 返回文件路径 | 返回文件路径 |

- Java 这一格出在 JDK 8 `BasicFileChooserUI.ApproveSelectionAction`：普通路径会走
  「是目录就 `changeDirectory`」，但带引号的多选路径在更早的分支被 `createFileObject`
  收进 `selectedFiles`，随后直接 `approveSelection()`，没再做目录判断。
- Python 侧是 Windows 原生文件对话框。用 Win32 消息把带引号路径写进文件名框、再点「打开」
  实测：弹窗保持打开、结果未返回；换成真实 `.xlsx` 才关闭并返回该文件。

### 28.2 修法

`FolderAwareChooser` 继承 `JFileChooser`，覆盖 `approveSelection()`：选中项里有目录时，
清空选择、`setCurrentDirectory(目录)` 后直接返回，不调用 `super.approveSelection()`；
只有真正选到文件才放行。点击虚线区打开的选择器改用这个类，多选与四档过滤器等设置不变。
不带引号的路径仍由 JDK 自己进目录，覆盖层对它是透明的。

### 28.3 守卫与验证

- Swing 自检新增 `folder_path_entry`：走弹窗自己的 `ApproveSelectionAction`
  （回车与「打开」是同一条路），依次验证带引号目录、不带引号目录都进目录且不产生确认事件，
  最后验证真实 `.xlsx` 仍确认一次并原样交出路径。
- 变异抽查：把 `approveSelection()` 改回无条件 `super`，自检两条变红
  （带引号的文件夹路径回车后没进入该目录 / 被当成文件交出去了），
  逐字节还原后哈希一致、自检转绿。
- `构建验证.bat` 十步全过；`界面双端对撞.bat` 仍为 235 键逐键一致（本轮不加控件）。

## 29. 原始表的两行合并表头：按参考表的形状压成一行

用户提供的原始表第一行是分组名、第二行是子项：`技术公司` 横跨 4 列，第二行是
`小计 / 高层 / 中层 / 普通员工`；左侧 `序号`、`单位名称` 等字段纵向合并两行。
同一份工作簿的第二页给出了期望形状：表头一行，组名与子项用 `-` 连接。
改造前这种文件在合并检测处被整份拒绝，用户只能先在 Excel 里手工改表。

### 29.1 放行规则

| 条件 | 不满足时 |
| --- | --- |
| 合并区只在第一个 Sheet | 整份拒绝 |
| 每一处合并区都从第 1 行开始 | 整份拒绝（第 2 行里的子合并属于另一种布局） |
| 只能是跨两行的单列纵向合并（`A1:A2`）或只横跨第 1 行的多列合并（`J1:M1`） | 整份拒绝（三行表头、2x2 块都不猜） |
| 至少一处跨两行（深度固定为 2） | 整份拒绝（单行表头上的合并仍拒绝） |

压平方式：先把每个合并区左上角的值铺满矩形，再逐列按行收集非空且与上一行不同的标签，
用 `-` 连接。纵向合并在铺值后两行文字相同，去重后只留一份，所以 `序号` 不会变成
`序号-序号`；横向合并把组名铺到组内每列，与第二行子项拼成 `技术公司-小计`。
压平后的表头继续走原来的空表头、重名、拼音与类型推断规则，日志在 `[已解析]` 行补一句
`合并表头按 2 行展开`。

## 32. 空表（只有表头）手工指定主键不再被拒绝

用户反馈：只有表头的空表导入后，在结构预览里勾一个主键，点保存被拒
“没有数据行，无法校验主键”。

### 32.1 根因与口径

两条线的 `validate_primary_key` / `validatePrimaryKey` 在类型检查之后、逐行校验之前
都硬写了一道零行闸门，于是空表无论勾什么主键都保存不了。

非空与唯一在空集上天然成立：零行表不存在违反约束的行，手工指定主键应当放行，

自动选键仍需要数据来判断，`select_primary_key` / `Infer.selectPrimaryKey` 的零行分支

“注意：没有数据行，无法校验主键”。

修法是删掉零行闸门，逐行校验在零行时自然空转返回通过；类型检查保持在最前。

## 33. Java 使用说明正文字号折算

用户反馈：Java GUI 的「使用说明」正文太小，同一份说明在 Python 端显示正常。

### 33.1 根因

说明正文的样式来自 `ui_help.py` 的 `STYLE`，其中 `body { font-size: 10.5pt }`。
Qt 按 96dpi 把 pt 折成 px（10.5pt → 14px）；Swing 的 HTML 渲染器按 72dpi 折
（实测 `14pt` 与 `10.5px` 的离屏渲染逐像素完全相同），于是同一份 CSS 在 Java 里
只剩约 7.9px，比左侧目录还小。问题在单位折算，不在字体族或窗口缩放。

### 33.2 修法

`HelpDialog.swingHtml()` 只把 `font-size: Npt` 按 96dpi 换成 `N×4/3 px`，
其余样式与正文一字不动；Python 端继续用原 CSS。折算后两端实际像素字号一致：
正文 14px、h2 18.7px、h3 15.3px、pre 12.7px。左侧目录仍用 Swing 默认字号，
与 Python 的 `QListWidget` 默认字号持平，不跟着放大。

## 34. 「关于」框首屏裁字

用户反馈：Java GUI 的「关于」框首屏文字显示不全，要拖大窗口才能看全。

### 34.1 根因

版本 / 提交 / 构建日期三行原来用 `GridLayout(3, 2)`：两列永远等宽，
内容宽 356px 时每列固定 171px。本机 Swing 默认字体 SimSun 18px，构建日期

（`JTextField` 的首选宽不含左右各 2px 的 margin），窗口在长提交号或大字号下
只会变宽，不会挤掉文字；关闭按钮那一行也不再写死 30px 高。拍照器 `UiShot`
不再给「关于」写死 380x168，避免把裁字藏进快照。

## 37. Java 图形版日志字号放大

现场反馈"凡是日志的地方，日志文字大小太小了，基本看不清"。Java 图形版的日志

  `Monospaced`：它的中文回退正好占两格，放大后表格仍然对齐。
- 字号先定 14：比原值大约 17%，在 1080p 上已经能和正文分清。首屏日志后来再次被判
