# 选型工作表与验收细节

## 决策顺序（每一步都要留下结论）

1. **先盘点已有能力**：JDK 8 标准库、已打包的依赖、Python 侧对应实现是否构成
   "必须逐用例对齐"的规范。已有库能覆盖的，不新增第二个同类库。
2. **列候选，至少两个**（含"自研"这一项），逐个填下面的表。
3. **过闸**（硬性条件，缺一即淘汰，见 SKILL.md 的七道闸）。
4. **双栈对齐条款**：Python 与 Java 输出要逐项一致的功能，库只能当"参考实现"或"探针"；
   进产品路径前必须包一层，并在 Python 侧金标准语料上全绿。
   库的输出与本项目既定语义冲突时，改库的用法或换库，**不许悄悄改 Python 语义去迁就库**。
5. **先做探针**：在 verify 模块或临时分支写最小可运行用例（半天到一天），喂真实语料
   （用户现场文件、边界样例、异常样例），与基线比输出。探针不过就换候选或自研，
   不把"README 说支持"当验证。
6. **落地**：版本属性与版本号进父 pom 的 `dependencyManagement`；app pom 只引用不带版本；
   pom 注释写"为什么选它、淘汰了谁、体积/许可/Java 8 的结论"。
   `mvn dependency:tree` 输出与探针结论进提交说明。
7. **验收**：跑 `java\构建验证.bat` 十步闸门、`java\界面双端对撞.bat`、两栈用例集；
   涉及执行/导入语义的，再跑真库 G 组。任何一步红都不算落地。

## 候选表怎么填

| 列 | 填什么 |
|---|---|
| 坐标与版本 | `groupId:artifactId:version`，只写具体版本 |
| 最近稳定版时间 | 阿里云镜像 `maven-metadata.xml` 的 `lastUpdated` 或版本目录，写年月 |
| Java 8 | 支持到哪个版本；class major 必须 ≤ 52 |
| 许可证 | Apache-2.0 / MIT / BSD / EPL 可用 |
| 传递依赖与体积 | `mvn dependency:tree` 输出的新增 jar 总增量 |
| 离线胖 jar | 有无 native、运行时下载、`META-INF/services` 冲突 |
| 可验证性 | 能否用现有金标准或真实语料逐用例比对 |
| 淘汰理由 / 选定理由 | 一句话 |

## 反模式（出现即停）

| 说法 | 现实 |
|---|---|
| "这个只能自己写" | 先列候选再下结论；没查过国内镜像不算查过 |
| "用最新版总没错" | 最新版可能是 RC；只认稳定版并钉死版本 |
| "三年没更新也没事" | 默认淘汰；例外要三条证据同时成立 |
| "SNAPSHOT 和正式版一样" | 不可复现构建，禁止 |
| "License 以后再说" | 打包前必须清楚；copyleft 不能进单 jar |
| "有 CVE 但没用到那个类" | 需要可达性证据与记录，不能拍脑袋 |
| "胖 jar 大一点无所谓" | 绿色 JRE 交付对体积敏感，超预算要写理由 |
| "库说它对，Python 那边改一下" | 双栈语义由金标准定，不由库定 |
