# 版本号判据的细节

用户 2026-10-23 定的规则："做完一个功能的时候，或者修复完一个问题的时候，你需要评估
是否需要升级版本号。"每一次收尾除了跑验证与提交，还要显式判断版本号动不动，并把结论
和一句理由写进汇报里——升与不升都要说，不说不等于判断过。

## 三档怎么定

先答一个问题：**这轮之后，老版本用户有没有"以前做不到、现在能做"的一件事？**

- 有，且老做法原样还能用 → **升 minor**（`2.0.x → 2.1.0`）。新增页签、新增按钮、
  新增一类交互、**新增一条执行/处理通道**（例如整库 dump 走逐条提交、手写脚本仍走按文件
  事务）、新增开关、CLI 新增参数、新增产物形态、交付件里新增可选字段，全在这一档
- 没有，只是"以前那件事现在做得更对 / 更稳 / 更快 / 更好看" → **升 patch**
  （`2.1.0 → 2.1.1`）。缺陷修复、文案订正、字号颜色间距、内部实现替换而输入输出形状不变
- 老做法**不能**原样用了 → **升 major**（`2.x → 3.0.0`）。同输入产出不同含义的结果且
  不告知就升级会出事：`conn.ini` 键位改名、CLI 参数含义变化、产物目录结构与启动方式变化、
  交付件形状旧版读不了、去掉或合并一个既有能力、执行语义从"可回滚"变成"已落库"这类
  用户已依赖的承诺改变

补充条款：

- 只改测试用例、只改文档、只改构建脚本且不影响交付物 → **不升**，在提交信息里写明"版本号不动"
- 一次会话做了多件事：按其中最重的一档定，一次升到位，不要每个 commit 升一次；
  升 minor 时 patch 归零（`2.0.10` 的新能力 → `2.1.0`，不是 `2.0.11`）
- 已经交付过某个版本再改东西 → 必须升，不能让用户手上两个同名包内容不同
- **兜底**：patch 升到 `x.y.9` 之后还要再升，先停下来重判——一路只升 patch 通常意味着
  把"新增能力"错记成了"修复"。本项目 2026-10-25 就被用户抓到这一条：dump 执行通道、
  脚本清单、交互引导样式都是"以前做不到现在能做"，却连着升成 `2.0.6`…`2.0.10`，
  更正为 `2.1.0`
- major 不攒着等"大 rewrite"：判据命中就升，哪怕只改一处不兼容；宁可 `3.0.0` 早点出现，
  也不要让用户按 `2.x` 理解一个语义已经变了的包

## 改哪里

取值唯一来自 `version.py` 的 `APP_VERSION`（窗口标题、《关于》、`--version`、随包 appinfo
都读它），另有 **9 处写死的字符串**要一起改：

- 四个 pom 位置：根 pom 的 `<version>` 与 `<app.version>`、app 与 verify 的 `<parent><version>`
- `java/构建验证.bat` 里的 jar 名（**这个文件必须保持 CRLF**，用按字节改的脚本，别用 `sed -i`）
- `help_doc.py` 与 `java/assets/conn.ini` 示例命令里的 jar 名（`help_doc.py` 改完要
  `java/tools/check_generated.py --write` 重导 `HelpDoc.java`）
- `RELEASE.md` 的两处产物名

`README.md` 不在此列：用户向文档不写版本号（`W29e` 反向核，写进去就红），改版本时不要动它。

`pack_test.py` 的 `T15` 逐处把这些字符串与 `APP_VERSION` 核一遍：**改版本前先跑一次确认
起点干净，改完再跑一次确认没漏**；产物目录名 `excel2mysql-java-<版本>-win64` 随 pom
自动变，不用手改。升过版本要等用户开口才重打交付包，但汇报里必须点明"包还是旧版本"。

## 阶段后缀（alpha / beta / rc）

用户 2026-10-23 补的口径："版本号类型有 rc，alpha 等，按照开发阶段进行版本号命名。"
阶段是**版本的属性**，不是另开一条号段，后缀直接写在 `APP_VERSION` 里（仍然只有这一个
来源）：`1.1.0-alpha.1`、`1.1.0-beta.2`、`1.1.0-rc.1`。窗口标题、《关于》、`--version`、
jar 名、产物目录名会自动带上后缀，`T15` 按整段核——只截 `X.Y.Z` 的话"1.1.0-rc.1 vs
1.1.0"会被判成一致，那正是这条守卫要拦的漏改。

三种后缀各自代表"这版能承诺到哪一步"，别拿来当装饰：

- `-alpha.N`：这一批功能还没收口，界面上还会变。只发给内部或明确愿意容忍改动的人，
  不要拿去装现场机器
- `-beta.N`：功能收口、闸门全过，但**还没在真实环境验过**（客户的 MySQL 版本、真实那批
  Excel、现场的系统版本）。给自愿试点的人，同时说清验收还没做
- `-rc.N`：只剩验收结论没拿回来。期间**不加功能**，只修阻断性缺陷；每修一处就进一个序号
- 转正：`1.1.0-rc.2` 验收通过 → 发 `1.1.0`，**号不变、只去后缀**（不要再 +1，否则
  "1.1.0 才是正式版"这个承诺反而多了一次版本跳跃）。rc 期间若改了用户可见行为，
  它就不再是"候选"，抬一档（patch 或 minor）重新从 `-rc.1` 起

**默认不带后缀**：这条线的产物是要装到现场办公机上的工具，包名里带 `rc` 等于自己承认
"这版不算数"，现场验收凭证上不该出现这种字样。只有用户明确说"先给一版试试、还不作数"
时才加；加了就要在汇报里写清"这版是候选，转正时去掉后缀、号不变"。

机器判定：`T1` 只放行 `X.Y.Z` 或 `X.Y.Z-(alpha|beta|rc).N`（`rc1`、`rc`、`release`
这类写法一律红）；序号从 1 起、用点号分隔，是为了让后缀能机器判读，也为了 Maven 的
版本序（`1.1.0-rc.1 < 1.1.0`）与文件名排序同向。
